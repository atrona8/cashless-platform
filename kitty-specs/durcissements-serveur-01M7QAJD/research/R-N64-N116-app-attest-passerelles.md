### A2. Format d'une assertion App Attest (référence Apple, « Validating apps that connect to your server », section assertion)

(Rédigé de mémoire, page Apple non rechargée ; à recouper avant codage, voir risque R1.)

- L'app appelle `DCAppAttestService.generateAssertion(keyId, clientDataHash)`. Résultat : un objet **CBOR** `{ "signature": bytes, "authenticatorData": bytes }` (deux clés textuelles, pas de `fmt`, pas de `attStmt`).
- `authenticatorData` = 37 octets : `rpIdHash` (32, SHA-256 de `teamId.bundleId`) | `flags` (1) | `signCount` (4, grand-boutiste). Pas de données de clé attestée ici (le drapeau AT 0x40 est absent) ; l'aaguid et le credentialId n'y figurent pas.
- Serveur, dans l'ordre d'Apple : (1) `clientDataHash = SHA-256(clientData)` recalculé par le serveur à partir de la requête reçue ; (2) `nonce = SHA-256(authenticatorData ‖ clientDataHash)` ; (3) vérifier `signature` (DER ECDSA) avec la **clé publique conservée à l'attestation** sur `nonce` ; (4) `rpIdHash == SHA-256(teamId.bundleId)` ; (5) `signCount` **strictement supérieur** au compteur stocké (le compteur de l'attestation est 0, déjà contrôlé par `checkAuthData:` « compteur ≠ 0 ») ; (6) mettre à jour le compteur stocké.
- Piège connu : la signature porte sur `nonce` traité comme un MESSAGE (ECDSA-SHA256 hache donc une seconde fois). En Node : `crypto.verify('sha256', nonce, {key, dsaEncoding:'der'}, signature)` avec `createPublicKey` du SPKI. Ne pas passer `nonce` comme condensé déjà calculé. Dans les tests locaux on écrit aussi bien le signeur que le vérificateur : une erreur de double hachage serait invisible (R1).
- À stocker par terminal : `key_id` (credentialId, 32 octets, SHA-256 du point P-256), clé publique de l'attestation (SPKI DER ou point 65 octets ; le point 65 o. est déjà calculé par `uncompressedPoint()`, mais SPKI est ce que `node:crypto` relit sans conversion), `counter` (bigint, dernier signCount accepté ; 0 à l'enrôlement), horodatages. Le `receipt` d'Apple n'est pas exploité (comme aujourd'hui).

### A3. Conception proposée

**Stockage : table dédiée `device_app_attest_key`** (plutôt que des colonnes sur `device`) :
`device_id uuid PK REFERENCES device(id)`, `operator_id uuid NOT NULL REFERENCES party(id)`, `key_id bytea NOT NULL CHECK (octet_length=32)` UNIQUE, `public_key bytea NOT NULL` (SPKI P-256), `counter bigint NOT NULL DEFAULT 0 CHECK (counter >= 0 AND counter <= 4294967295)`, `enrolled_at`, `last_assertion_at timestamptz`. RLS activée et forcée, politique `tenant_isolation` comme 0022:219-221. Raisons : (a) pas de UPDATE de colonnes sur `device` (triggers edge 0063, contraintes `device_attestation_os`), (b) la clé et le compteur n'entrent pas dans la réplication passerelle, (c) une ligne seulement pour iOS (CHECK/trigger : le terminal doit être `os='IOS'`). Alternative rejetée : colonnes `app_attest_key_id/public_key/counter` sur `device` (0063 réplique l'INSERT, `last_seen_at`-like mises à jour sur une table très lue).

**Migration 0090** (nom suggéré `0090_app_attest_keys.sql`), tous droits dans `post-roles.sql` (règle du dépôt : « les droits par rôle sont posés par post-roles.sql, jamais dans la migration ») :
1. `store_device_app_attest_key(p_device uuid, p_key_id bytea, p_public_key bytea)` RETURNS void, SECURITY DEFINER, `search_path = public, pg_temp`. Appelée par `enrollment.service.ts` **dans la même transaction `tx.run`, juste après `enroll_device`** : atomicité de l'enrôlement conservée (échec => rollback complet), signature d'`enroll_device` **inchangée** (pas de nouvelle signature d'une fonction à 13 paramètres, pas de DROP, pas de réécriture des tests tests_device_enrollment/tests_enrollment_event_state). Contrôles : `assert_tenant`/`app.operator_id` = `device.operator_id`, `device.os='IOS'`, `device.attestation_kind='IOS_APP_ATTEST'`, statut ≠ REVOKED, une seule ligne par terminal (`INSERT` simple => unique_violation sinon), tailles. Sans cette fonction, l'API ne peut rien écrire (cashless_app n'a ni INSERT ni UPDATE).
2. `advance_app_attest_counter(p_device uuid, p_key_id bytea, p_counter bigint) RETURNS boolean` : `UPDATE device_app_attest_key SET counter = p_counter, last_assertion_at = now() WHERE device_id = p_device AND key_id = p_key_id AND counter < p_counter AND operator_id = <session>` + jointure sur `device.status <> 'REVOKED'` ; rend `FOUND`. **C'est la mise à jour atomique** : une seule instruction conditionnelle ; deux assertions concurrentes de même compteur : le verrou de ligne d'UPDATE sérialise, la seconde voit `counter < p_counter` faux et rend faux (rejeu refusé). Pas de SELECT puis UPDATE.
3. `get_device_app_attest_key(p_device uuid)` RETURNS TABLE(key_id bytea, public_key bytea, counter bigint) : **inutile si SELECT reste accordé** (cashless_app a SELECT sous RLS ; `device.public_key` est déjà lu ainsi par la garde). Recommandation : garder SELECT par défaut (aucun droit nouveau), pas de fonction de lecture. Si le porteur préfère ne pas exposer la clé en SELECT : `REVOKE SELECT` + cette fonction (2e EXECUTE).
4. `post-roles.sql` : `REVOKE INSERT, UPDATE, DELETE, TRUNCATE ON device_app_attest_key FROM cashless_app;` (le défaut de roles.sql:15 l'accorderait) et ajout des deux fonctions à la liste EXECUTE de `cashless_app` (près de `enroll_device`, :462). **Il est impossible de ne rien accorder du tout** : il faut deux EXECUTE sur des fonctions DEFINER étroites (écriture à l'enrôlement ; avance du compteur). Aucun droit de TABLE ajouté ; à dire explicitement au porteur dans le plan (« aucun droit ajouté à cashless_app » est tenu pour les tables, pas pour EXECUTE). Alternative rejetée : un rôle dédié (surdimensionné pour une capacité sans route).
5. Mettre à jour les tests de droits : `packages/ledger-sql/tests/tests_execute_grants.sql` (liste exacte des fonctions de `cashless_app`, comptes « N fonctions » dans les messages), `tests_device_rights.sql` (nouveau § : INSERT/UPDATE/DELETE direct refusés à `cashless_app`, EXECUTE accordé aux deux fonctions seulement).

### A5. Risques
- R1 (crypto, **à faire relire par une personne**, `ios-app-attest-assertion.ts` et la fonction SQL de compteur) : double hachage ECDSA de l'assertion non vérifiable avec des vecteurs auto-générés ; exiger un vecteur d'assertion réel d'Apple (ou la vérification de l'implémentation de référence d'Apple) avant la mission 12.
- R2 : l'`aaguid`/environnement `development` : l'assertion n'a pas d'aaguid ; la distinction dev/prod ne se rejoue pas à l'assertion (portée seulement par la ligne stockée : un terminal enrôlé en prod ne vient pas de dev).
- R3 : EXECUTE ajouté à `cashless_app` (deux fonctions DEFINER) : écart à signaler avant codage (règle « jamais en silence » : c'est un droit supplémentaire, même étroit) ; options : (i) 2 fonctions, (ii) une seule fonction qui insère OU avance. Recommandation : (i).
- R4 : `signCount` Apple peut ne pas être strictement monotone en cas de bug d'app/restauration ; la règle du porteur (strict) l'impose : un terminal bloqué se ré-enrôle.
- R5 : clé stockée sur un terminal REVOKED puis ré-enrôlé : nouveau `device.id`, nouvelle ligne ; `key_id` UNIQUE global refuserait une réinstallation qui rejoue la même attestation (cas voulu).
